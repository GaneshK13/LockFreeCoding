Chapter 4
	CAS based vulnerabilities
		ABA problem (memory reclamation problem)
			t1 reads A from a shared atomic location
			prepared to perform CAS
			before t1 executes it, t2 runs
			t2 changes the value from A -> B -> A
			t1 resumes and executes its CAS
			CAS comparison succeeds as location holds value A which matches what t1 read
		ABA leads to use-after-free crash:
		Hardware Level Solution
			DWCAS
				CMPXCHG16B instruction
				pair the pointer with version counter called tag
				every modification to a pointer, increments the tag
				16 bytes aligned [alignas(16)]
				compiler must emit CMPXCHG16B
				GCC/Clang - compile with the cx16 feature enabled, included in march=native or march=x86-64-v2 target flags
				ARM64: CASP Instruction pair on ARMv8.1-A +
			Hazard Pointer (C++ 26)
				preventing freed memory from being reallocated while any thread holds a reference to it.
				before dereferencing a pointer to a shared object, it publishes that pointer into a per-thread hazard slot
				lifetime of hazard pointer protection: window btw slot publication and its release
				Hazard Pointer library manages a per-thread retirement list that accumulates retired objects
				Memory pressure from deferred reclamation
				bounded memory overhead is the cost of the safety guarantee
				Keep the protection window as short as possible
				release hazard slots immediately after the dereference that required them
				used in lock free linked list, trees, graphs for protecting multiple nodes at a point
			Epoch-based reclamation & RCU Dynamics
				Cheaper when
					1. frequent read operations
					2. traversals are deep
					3. overhead of per-dereference protection accumulates into a measurable fraction of operation's total cost
				lower per operation overhead for read-heavy conditions
				Global Epoch & 3 Epochs: 1 current & 2 preceding
				Before reading, announce participation by recording current epoch into per-thread epoch variable
				Before deleting the object, places it into a retirement list tagged with the current epoch
				EBR is efficient compared to hazard pointer: thread participation is declared once per operation, not once per pointer dereference
				thread that stalls inside epoch, perhaps due to preemption, page faults, or long computation, blocks the global epoch from advancing & prevents reclamation from making progress
				EBR ties reclamation progress to the slowest active thread
				RCU: read, make a copy of the object read, update the copy, replace the updated copy with the original
				RCU pattern shines in configurations where reads vastly outnumber writes
				RCU is the dominant synchronization mechanism in the Linux Kernel for data structures like routing tables, device driver registries etc
				Which one to choose: Hazard or EBC
					1. read-to-write ratio: reads dominates & traversals are heavy, EBR's once per operation announcement cost makes it more efficient
					2. latency-predictability: if threads stall inside read side critical sections, use hazard pointers as for EBR, global epoch won't progress which would put more pressure on the allocator memory growing
					3. reclamation latency requirements: EBR reclaims in batches

Chapter 5
	Lock Free Queues
		SPSC
			genuine wait freedom
				no lock
				no CAS loop
				no spins on CAS failures
			1 thread produces & 1 consumes
		Bounded MPMC (Dmitri Vyukov)
			assign each slot in the array it's own sequence number
			slot can have four states:
				1. ready to be written
				2. being written
				3. ready to be read
				4. being read
			producer claims the slot by incrementing the tail counter & then waiting for it's claimed slot sequence no. to reach 'slot is ready for writing'
			consumer claims the slot by incrementing the head counter & then waiting for it's claimed slot sequence no. to reach 'slot is ready for reading'
		Unbounded MPMC (Michael Scott Queue)
			Burst size cannot be bounded at design time
			Singly linked list: head & tail pointers
			head: sentinel node
			sentinel node design eliminates the need to handle the empty queue
			Enqueue appends new node at tail
			Dequeue advances the head past the sentinel and returns the data from the new sentinel, which was the old front element.
			2 step nature of enqueue operation:
				link the new node at the end of the list
				and advance the tail pointer to the new node
				between these 2 steps there is a window where the tail pointer lags behind the actual end of the list.
				Any other thread that arrives during this window must detect inconsistency and HELP complete the lagging tail advance before proceeding with its own operation.
			variable load profiles without dropping items or blocking producers

Chapter 6
	Lock Free Stacks & Linked Lists
		Treiber Stack and Elimination Backoff
			avoid CAS bottleneck on top when multiple threads fighting
			fundamental scalability problem when serializing operations through a single shared pointer
			avoid ABA by pairing it with hazard pointers or EBR approach
		Elimination backoff
			to turn the contention problem into a throughput advantage
			push & pull that arrive simultaneously & collide on CAS can eliminate each other without touching the stack at all
			reducing the load on the central CAS bottleneck
			shared collision array
			if no elimination partner is found within the waiting window, the thread falls back to the central stack CAS
			Pusher spins on the state for bounded no. of iterations
			Elimination layer is an optimization layer
			Approach can be applied to any data structure where inverse operations can cancel each other
			Under light contention, elimination layer adds overhead
			Good for moderate to high contention with a balance mix of push & pull operations arriving simultaneously
		Harris's Algorithm for Safe List traversal
			LinkedList exposes every node in the structure as a potential modification point
			logical deletion using pointer marking
			logically deleted node is still present in the list
			deletion: a two phase structure
			marking mechanism: lowest bit of the next pointer
			lowest bit of any valid node pointer is always zero
			repurpose that bit as a deletion mark
			marking CAS is a single atomic operation on a single word, it cannot race with other thread
			sentinel head & tail node are never removed
			no next pointer is null except for tail sentinel node
			locates two adjacent nodes:
				a predecessor & a current node
				predecessor's next pointer is not marked & points to current node
				current node either matches the search key or is the first node whose key is >= search key in ordered list
			During traversal, find() physically removes any logically deleted nodes [lazy cleanup]
